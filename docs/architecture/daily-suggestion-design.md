# Daily Suggestion Engine Design

## 1. Overview & Objectives

The Daily Suggestion Engine addresses the user's implicit question: "What should I do today?" by providing exactly **1 primary suggestion and 1–2 optional alternatives**. It shifts the product paradigm from being purely chat-first to being action-first, integrating smoothly into the core loop: **Understand User -> Suggest -> Act -> Capture -> Generate Memory -> Timeline**.

Aligning strictly with the "Quiet Companion" ethos, suggestions must be minimalist, low-friction, and entirely non-demanding. The engine actively guards against the companion becoming a coach or a source of nagging pressure; instead, it offers light, manageable, real-world actions to gently inspire the user.

## 2. Daily Suggestion Data Model & Schema

The Daily Suggestion entity represents a single structured recommendation generated by the AI. All database metadata is strictly stripped prior to injection into the client payload or LLM prompt.

### TypeScript Interfaces & Zod Validation

```typescript
import { z } from "zod";

export const DailySuggestionSchema = z.object({
  id: z.string().uuid(),
  userId: z.string().uuid(),
  primarySuggestion: z
    .string()
    .max(255)
    .describe("Actionable activity title or text"),
  supportingContext: z
    .string()
    .max(500)
    .describe(
      "Concise rationale (1-2 sentences) explaining why this fits today",
    ),
  alternatives: z
    .array(z.string().max(255))
    .min(1)
    .max(2)
    .describe("1-2 lightweight alternative options"),
  estimatedDuration: z.enum(["15m", "30m", "1h", "flex"]),
  categoryTags: z
    .array(z.string())
    .max(3)
    .describe(
      "Lightweight tags like 'outdoor', 'mindful', 'creative', 'routine-break'",
    ),
  createdAt: z.string().datetime(),
  status: z
    .enum(["pending", "accepted", "skipped", "alternative_requested"])
    .default("pending"),
});

export type DailySuggestion = z.infer<typeof DailySuggestionSchema>;

// The payload sent to the client, explicitly omitting sensitive DB metadata.
export type ClientDailySuggestion = Omit<
  DailySuggestion,
  "userId" | "createdAt"
>;
```

### Sanitization Guarantees

- Raw database primary keys, user UUIDs, timestamps, and row-level security parameters are stripped from payloads sent to the client and from the contextual data sent to the LLM during generation.

## 3. Suggestion Status Lifecycle State Machine

The Daily Suggestion moves through a well-defined lifecycle based on user interaction.

### Status States

- **`pending`**: The initial state. The suggestion has been generated and is presented on the `/today` screen.
- **`accepted`**: The user actively selected the primary suggestion or one of the alternatives with the intent to perform it.
- **`skipped`**: The user dismissed, passed on, or ignored the suggestion.
- **`alternative_requested`**: The user requested to see or pursue one of the generated alternatives instead of the primary suggestion.

### State Transitions & Rules

- **`pending` -> `accepted`**: User taps "Do this" on the primary suggestion. (Terminal State for this specific suggestion cycle).
- **`pending` -> `skipped`**: User taps "Skip" or dismisses the UI. (Terminal State).
- **`pending` -> `alternative_requested`**: User expands or clicks an alternative option.
- **`alternative_requested` -> `accepted`**: User confirms they will do the alternative. (Terminal State).
- **`alternative_requested` -> `skipped`**: User dismisses the alternatives. (Terminal State).

**Idempotency:** State transitions are idempotent; re-submitting an `accepted` status update for a suggestion already in the `accepted` state yields a 200 OK without side effects.
**Persistence:** These states will map directly to the upcoming Task 1.4 database migration containing the `daily_suggestions` (or `user_actions`) tables.

## 4. Input Context Assembly Specifications

To generate a relevant, personalized suggestion, the engine constructs a lightweight context payload without bloating the prompt token count.

### Personalization Inputs

These are derived from the existing `PromptContext` generated via `src/lib/ai/context-builder.ts` and `src/lib/ai/personalities.ts`:

- **`displayName`**: The user's preferred name. Safe fallback: `"Friend"`.
- **`companionVibe`**: The companion's personality (`Spontaneous`, `Reflective`, or `Creative`). Safe fallback: `"Spontaneous"`.

### Situational Context Inputs

- **Lightweight Context**:
  - Time of day: `morning`, `afternoon`, or `evening`.
  - Location/Environment preference: `indoor`, `outdoor`, or `weather-flexible`.
  - Available duration window: Context on how much time the user generally has (e.g., short 15m breaks vs. a 1h open window).
- **Anti-Repetition Context**:
  - A strictly bounded window of the most recent suggestion history (e.g., the last 3-5 days) is included to ensure the model provides variety.

## 5. AI Generation Contract & JSON Output Schema

The engine utilizes the OpenAI API using strict Structured JSON Output (`response_format: { type: "json_object" }` or explicit schema definition depending on the model version) to guarantee predictable parsing.

### JSON Output Schema Contract

```json
{
  "primarySuggestion": "Take a 15-minute walk without your phone.",
  "supportingContext": "You've been indoors most of the morning. A quick screen-free walk will clear your head and fits the spontaneous vibe.",
  "alternatives": [
    "Stretch by the window for 5 minutes.",
    "Make a fresh cup of tea and focus on the brewing process."
  ],
  "estimatedDuration": "15m",
  "categoryTags": ["outdoor", "mindful", "screen-free"]
}
```

### Prompt Guardrails

- **Brevity**: Hard limits on sentence length.
- **Low Friction**: Suggestions must be immediately executable in the real world with minimal preparation.
- **Zero Demands**: Explicit prohibition against assigning "homework," demanding long journal entries, or adopting a lecturing tone.
- **Vibe Alignment**: The generated text must seamlessly match the active companion vibe (e.g., playful for `Creative`, grounding for `Reflective`).

## 6. Security, Isolation & Multi-Tenancy

- **Server-Side Isolation**: Context assembly, prompt construction, and OpenAI generation are executed completely server-side. The module must use the `import "server-only";` pragma.
- **Data Fetching & RLS**: All user data retrieval must utilize the cookie-based SSR Supabase client (`src/lib/supabase/server.ts`). This guarantees that Row Level Security (RLS) is strictly honored based on the authenticated user ID (`auth.uid() = user_id`).
- **Zero Middleware Overhead**: Database checks, context fetching, and AI integration must entirely bypass `middleware.ts` to ensure edge-runtime performance is not penalized.

## 7. Explicit Non-Goals & Deferrals

To maintain project focus, the following features are explicitly out of scope for this task and are deferred to later phases:

- Complex trip planners or multi-day itineraries.
- Qdrant vector memory integration (Semantic search capabilities).
- Automated background CRON generation of suggestions (generation currently happens just-in-time or via specific user triggers).
- UI Screen Implementation (Deferred to AIC-402).
- API Route implementations and Database Migrations (Deferred to Task 1.3 and 1.4).
